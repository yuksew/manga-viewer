## 最も重大な 3 件

1. **索引層の試験がゼロ（変異 7/7 生存）。** 差分索引・削除の整理・削除範囲・表紙の失効・`user_version` の作り直しは、
   実走では正しいが、回帰を捉える網がない。直し方: 合成ルートで「2 回目 `rescanned=0`」「冊削除で `removed=n`」
   「別ルートを巻かない」「mtime 変更で `updated=1`」「`user_version` 不一致で作り直し」を結合試験に足す。
   M1〜M7 がすべて落ちることを確認する。
2. **差分索引の鍵がフォルダ冊の「頁の上書き」を見ない／壊れた DB が復旧しない。**
   (a) フォルダ冊の鍵は「フォルダ自身の mtime + 画像サイズの合計」。既存画像を同サイズで上書きすると `unchanged`
   のまま（実測）。いま DB が持つ `page_count` には影響しないが、p0-2c の表紙（`covers`）は古いままになる。
   頁の増減・差し替え同数はフォルダ mtime が変わるので検知できた。許容するなら設計に明記、しないなら鍵に画像の最大 mtime を足す。
   (b) 設計 §2.2 は「作り直せる物だけ入れる」方針だが、SQLite でないファイルを `--db` に渡すと
   `file is not a database` で終了 1 になり自動では作り直さない（`user_version` 不一致のときだけ作り直す）。
   利用者が DB を手で消すまで `index` も `list` も使えない。
3. **1 回だけ再現しない異常（原因不明）。** 最初の合成ルートで、削除の直後の `index` が
   `updated` / `removed` の値と実際の DB がずれた（`removed=0` のまま 50 行残り、次の実行で `removed=2`。別の実行では
   全冊が `updated=46`）。同じルートに、私が作っていない `a.zip` `b.zip` `empty.zip` が同時刻に現れていた。
   新規ルートで 5 回繰り返した削除の再現（5/5）と別の試験列では出ていない。ほかのプロセスがこの `tests/.tmp` 下に触れた疑いがあり、
   実装の欠陥と断定できない。ただ、削除の整理は 1 回の走査と DB の突き合わせで決まるため、
   走査中に外から冊が変わった場合の挙動（`unchanged` と `removed` の整合）は試験で押さえておくとよい。
