# p0 設計 — 高速漫画ビューア（ネイティブ GUI）

- 日付: 2026-10-30
- 位置づけ: **設計のみ。実装はしない。** 実装は Qwen へ小段カードで渡し、監査は Claude が持つ。
- 前提: HEAD `c116d49`、コードは `src/main.rs`（Hello, world!）だけ。検証の門と慣習は `docs/project-guide.md`。
- 先行ドラフト（ブラウザ UI + ローカルサーバ案）は利用者決定「ブラウザ UI は却下」と矛盾するため**破棄して全面書き直し**。

## 0. 根拠にする実測値（司令塔が実測済み。再実測しない）

- `D:\books` = 724 冊。典型は 1 冊 = 1 フォルダ + 中に ZIP 1 本。
- ZIP 内は PNG、`001.png` 連番、deflate 圧縮、平均 ~1.4 MB/頁、1 冊 ~28 頁・展開後 ~40 MB。
- Python zipfile で「索引 + 初頁展開」= 154 ms（Rust の目標は、これより十分小さいこと）。
- `cargo build --release` は通る（`cl.exe` は PATH に無いが `link.exe` 経由でリンクできている）。

## 0.1 絶対制約: 漫画の実ファイルに触らない

- Claude は `D:\books` / `D:\torrent` の中身を開かない（read/vision/unzip/listing 確認すべて禁止）。
- 試験・ベンチ・画面確認は**すべて合成データ**（`tests/.tmp/` 下に生成する合成 zip / フォルダ）で回す。
  Qwen のカードも同じ。実データでの合否は、完成後に**利用者が自分で** `--root D:\books` で起動して測る（§2.3）。
- 合成データの作り方は p0-1a で決める（§5）。実データの見た目・名前・内容を合成側に写さない。

## 1. 決定 A — 読む対象

| # | 決定 | 内容 |
| --- | --- | --- |
| A-1 | 冊の単位 | **ZIP（`.zip` / `.cbz`）1 本、または画像が直接入ったフォルダ 1 個**を 1 冊とする |
| A-2 | ルート | 1 つ指定（既定 `D:\books`、`--root` で変更）。走査は**ルート直下（深さ1）とその 1 階層下（深さ2）まで**。それより深くは見ない |
| A-3 | 冊の判定 | 深さ1・2 の各ディレクトリについて: ① 直下の `.zip/.cbz` は各々 1 冊 ② 直下に画像ファイルが 1 枚以上あれば、そのフォルダも 1 冊 ③ 深さ1のディレクトリはさらに子ディレクトリを見る。画像も zip も無い空のフォルダは冊にしない（一覧に出さない）。深さ3以降にしか画像が無い冊は**拾わない**（仕様） |

| A-5 | 頁順 | **名前の自然順**。`/` 区切りに正規化した ZIP 内パス（フォルダなら冊直下からの相対パス）を、大小無視・連続数字は数値比較（`2.png` < `10.png`）、同値なら先頭ゼロの長い方が後、で比べる。実装は `natord` ではなく自前でもよいが**同じ仕様の単体テストを必須**にする |
| A-6 | 壊れた冊 | **一覧には出る、開けない**。`status = broken` + 理由文字列（中央ディレクトリ読めない / 暗号化 / 頁 0 枚 / パスが UTF-8 でない 等）。一覧では×印と赤字、クリックで理由をステータス欄に出す。開いている途中の 1 頁が壊れているだけなら冊は開け、その頁に「この頁は読めません」を出して前後へは進める |
| A-7 | 安全弁 | デコード時に画素数上限を設ける（`image::Limits`、1 枚 100 MP 超は拒否＝その頁は読めない扱い）。ZIP 暗号化は非対応（broken） |

## 2. 決定 B — 「高速」の定義（4 項目すべてに合格線）

数値は**最初の合格線**。p0-2 / p0-3 のベンチ結果を見て設計者（Claude）が改訂してよい。ただし 4 項目すべてに線がある状態を保つ。
測定は **release ビルド・合成データ・ウォームキャッシュ（同じ測定を 1 回捨てて 2 回目から取る）**。

### 2.1 しきい値

| # | 項目 | 合格線 | 測り方（定義を厳密に） |
| --- | --- | --- | --- |
| **B-1** | ページ送り | **順送りで「入力 → 新頁が描画フレームに載る」p95 ≤ 100 ms、max ≤ 250 ms**（100 ms 間隔の連打 100 頁を含む）。部品予算: 1 頁ジョブ（バイト読み + デコード + 画面サイズへ縮小）が単スレッドで **p95 ≤ 80 ms**（合成 ~1.4 MB PNG、約 1500×2200） | 部品: p0-2b のベンチ（ジョブ単体を 200 回）。通し: p0-3c の `--autopilot reader` が内部でキー入力を注入し、入力時刻〜その頁を描いたフレーム終了時刻を記録して p95/max を出す |
| **B-2** | 起動 → 一覧 | **インデックスキャッシュ有りで、`main()` 開始から一覧グリッド初回描画まで ≤ 1.0 s**。可視範囲のサムネイルが埋まるまで ≤ 1.5 s（合成 724 冊） | p0-3c の `--autopilot startup` が `Instant` で記録。外側の確認として PowerShell `Measure-Command` で `--autopilot startup` の終了までの壁時計も取り、≤ 1.3 s |
| **B-3** | 初回インデックス（DB 無し・合成 724 冊） | **(a) 先頭 100 冊が一覧に出るまで ≤ 1 s、(b) 全 724 冊の構造索引（冊・種別・頁数・状態）完了 ≤ 5 s、(c) 表紙サムネイル生成は背景で進み、可視範囲優先、100 冊分（実寸表紙入り）≤ 5 s**。一覧は完了を待たず逐次増える | p0-1b のベンチ（a,b）と p0-2c のベンチ（c）。(c) は 100 冊で測り、724 冊では ×7.24（≈ 36 s 以内を背景で）と見なす |
| **B-4** | ZIP の初期ロード | **冊を開く操作 → 初頁が表示されるまで ≤ 300 ms**（28 頁の冊、および 1000 エントリの冊の両方）。ZIP 全体を展開しない（中央ディレクトリ + 初頁のみ） | p0-2b のベンチ（open〜初頁デコード完了）と p0-3c の通し |
| B-5 | メモリ（補助線） | 1 冊を開いたまま 100 頁（合成 ~1.4 MB PNG）を巡回しても **RSS ≤ 500 MB**、キャッシュ予算は 192 MB で頭打ち | p0-2b / p0-3c で巡回後に `memory-stats` で読む |

注: B-3(b) は頁数を数えるために各 ZIP の**中央ディレクトリだけ**を読む。画像本体は読まない。表紙の PNG デコードは避けられない CPU 仕事なので、構造索引(b)と分けて背景処理にし、5 s の線に載せない（これが「724 冊 ≤ 5 s」を現実的にする最重要の分割）。

### 2.2 構造（線を守るための作り）

- **索引キャッシュ**: `%LOCALAPPDATA%\manga-viewer\index.db`（SQLite、WAL）。環境変数 `MANGA_VIEWER_DATA` があればそこを使う（試験用）。作り直せる物だけを入れる。`PRAGMA user_version` が合わなければ**捨てて作り直す**（移行や控えは作らない）。
  - `books(id INTEGER PK, path TEXT UNIQUE, kind TEXT, mtime_ns INTEGER, size INTEGER, title TEXT, page_count INTEGER, status TEXT, error TEXT, scanned_at INTEGER)`
  - `covers(book_id INTEGER PK REFERENCES books(id) ON DELETE CASCADE, w INTEGER, h INTEGER, jpeg BLOB)`（サムネイル。別表にして一覧読み込みで BLOB を引かない）
  - **頁リストは保存しない**（冊を開いたとき中央ディレクトリ / readdir から作る。古くならず、DB が小さい）。
  - 冊の鍵 = `path + mtime_ns + size`。ZIP は ZIP ファイル自身の値。フォルダ冊は `mtime_ns = フォルダの mtime`、`size = 直下の画像ファイルのサイズ合計`（readdir の DirEntry メタデータで足りる）。鍵が同じ冊は再スキャンしない。
- **起動の流れ**: ①DB から `books`（BLOB なし）を読み、即座に一覧を描く（B-2）→ ②背景スレッドでルートを走査して DB と突き合わせ（追加・変更・削除）、変化分だけ一覧へ反映 → ③表紙が無い冊のサムネイルを背景で作る。**起動時の再走査で UI を止めない**。
- **サムネイル**: 表紙 = 頁順の先頭。幅 ≤ 240 / 高さ ≤ 340 に縮小して JPEG（品質 80）で `covers` へ。専用の rayon プール（論理コア数/2、最小1）。GUI から「いま見えている冊」を優先キューの先頭へ積む。
- **頁デコード**: 専用の rayon プール（論理コア数−2、最小2。サムネイルのプールとは別）。ジョブ = ZIP/フォルダからバイト読み → `image` でデコード → **画面（物理ピクセル）に収まるサイズへ縮小** → RGBA。ZIP の読みは冊ごとの `Mutex<ZipArchive>` 下で**バイト取り出しだけ**を行い、デコードと縮小はロック外で並列に回す。
- **頁キャッシュ**: 縮小後 RGBA を `(冊世代, 頁, 画面サイズ)` で保持。バイト予算 192 MB、予算超過は表示頁から遠い順に捨てる。GPU テクスチャは表示頁と前後各1頁だけ。
- **先読み**: 表示頁 `p` に対し、直前の移動方向を前方として優先順 `p, p+1, p+2, p+3, p-1`（後退中は鏡像）。頁を移ると、**未着手で窓の外に出たジョブは取り消す**（世代トークンで判定）。窓サイズ変更は 150 ms デバウンスして、キャッシュの画面サイズ違いを無効にする。
- **ページ送りが速く見える理由**: 先読みが効いていれば入力時はキャッシュ命中（テクスチャ作成のみ）。連打で追い越されても、並列ワーカー × 頁ジョブ ≤ 80 ms で 100 ms 間隔の連打に追従できる、という構造の勘定（B-1 の部品予算の根拠）。

### 2.3 実データでの合否（利用者が手元で）

`MV_TRACE=1` でアプリが B-1〜B-4 の実測値（起動→初描画 ms、冊オープン→初頁 ms、頁表示 ms の p95 など）を stderr に 1 行ずつ出す。利用者が `D:\books` で起動してその行を持ち帰る。Claude/Qwen は実データを読まない。
実データの cold キャッシュ（OS のファイルキャッシュが冷えた状態）と、D: が HDD か SSD かは未確認。数値が外れたらまずこれを疑う。

## 3. 決定 C — GUI フレームワークと画面

### 3.1 選択: **egui / eframe（glow バックエンド）**

| 候補 | 評価 |
| --- | --- |
| **egui / eframe** ◎採用 | 純 Rust（C 依存なし）。即時モードで「状態 = 画面」。`ScrollArea::show_rows` で行仮想化でき、724 冊でも描画対象は見えている行だけ。`ctx.load_texture` で ColorImage を直接 GPU へ上げられ、裏スレッドからの `request_repaint()` で**アイドル時は CPU を使わない**。キー入力・ビューポート操作・スクリーンショット（`ViewportCommand::Screenshot`、監査用）が揃う。1 枚絵 + グリッドという p0 の画面に過不足なし |
| iced | Elm 型で整理されるが、画像グリッドの仮想化と大量サムネイルの扱いは自前の部品が増える。画像ビューア用途の実績が egui より薄い。却下 |
| slint | 宣言 UI は綺麗だが独自 DSL + ライセンス条件の確認が要る。画像を大量に動的投入する用途で得るものが小さい。却下 |
| Tauri / WebView 系 | 実質ブラウザ UI。利用者が却下済みの方向。却下 |
| fltk-rs / native-windows-gui / Win32 直 | C/FFI 依存または手書き量が多く、Qwen に小段で渡す設計に向かない。却下 |

- eframe は `default-features = false, features = ["glow", "default_fonts"]` から始める（C ビルドを避け、コンパイル時間を抑える）。落ちたら default に戻してよい（その事実を報告に書く）。版は `cargo add` が入れる最新安定版を `Cargo.lock` で固定し、p0-0 の報告で版数を書き戻す。
- **日本語フォント**: egui 同梱フォントは CJK を含まない。起動時に `C:\Windows\Fonts\` の `YuGothM.ttc` → `meiryo.ttc` → `msgothic.ttc` の最初に存在するものを `FontData`（index 0）として最優先に登録する。1 つも無ければ既定のまま（豆腐表示だが落ちない）。

### 3.2 p0 の画面（これだけ。見開き・ズーム・回転・検索・しおりは範囲外）

1. **一覧グリッド**: 表紙サムネイル + 題名（フォルダ名 or ZIP の拡張子抜き名）+ 頁数。列数は幅に応じて自動。サムネイル未生成はプレースホルダ。broken は×印・赤字。ソートは自然順で固定。上部に現在のルートと「N 冊 / 走査中…」表示。ダブルクリック or Enter で開く。
2. **閲覧**: 1 頁ずつ、画面に収まる全体表示（アスペクト維持）。キー: **←/Space/PageDown = 次、→/PageUp/Backspace = 前**（漫画の右→左綴じ前提。向きは `const READ_RTL: bool` 1 箇所で反転できる）、Home/End = 先頭/末尾、Esc = 一覧へ戻る（一覧のスクロール位置を保つ）、マウスホイール下 = 次。下端に `頁 N / M` と題名。
3. 画像が読めない頁はエラー文のプレースホルダ。

### 3.3 CLI

`manga-viewer [--root <dir>]`（引数なし = GUI 起動）/ `manga-viewer index --root <dir> [--db <path>]`（索引のみ、件数と所要を出す）/ `manga-viewer list [--db <path>]`（DB 内容を TSV で出す、試験用）/ `--autopilot <startup|reader> --root <dir>`（§2.1 の通し測定。終了コードで合否ではなく数値を出す）。引数解析は `clap`（derive）。

## 5. 実装の割り方（Qwen へ渡す小段。1 カード = 1 コミット）

全小段共通の**合格門**: `cargo fmt --check && cargo clippy -q && cargo test && cargo build`（すべて exit 0）。PATH に `cargo` が無いシェルでは `%USERPROFILE%\.cargo\bin` を足してから。コミットは日本語一行文。ベンチは `#[ignore]` の試験にし、`cargo test --release -- --ignored --nocapture <名前>` で走らせ、出力に `BENCH <名前>=<数値>ms` 形式を 1 行ずつ出す（既定の門に載せない＝機械差で門が落ちないため。数値は報告に貼り、判定は監査）。

| 段 | 内容 | 追加の検査 |
| --- | --- | --- |
| **p0-0 依存の関門** | `Cargo.toml` に §4 の依存を**1 つずつ** `cargo add` → `cargo build --release` で通ることを確認（rusqlite bundled と eframe は個別に）。`.gitignore` に `tests/.tmp/` を足す。`src/main.rs` は触らない（未使用依存は警告が出ない）。報告に版数・落ちた依存・直した方法を書く | 4 つの門 + `cargo build --release` 通過。rusqlite が落ちた場合はそこで止めて報告（Build Tools 導入は利用者判断） |
| **p0-1a 冊の発見と頁リスト** | `lib.rs` 化。`scan`（A-2/A-3 の走査 → `Vec<BookEntry{path,kind,mtime_ns,size,title}>`）、`book`（`Book::open(path)` → 頁リスト（A-5 の自然順・A-4 の拡張子フィルタ）/ `read_page_bytes(i)`、ZIP とフォルダの両方、`BookError`）、自然順関数。`tests/common` に合成データ生成（合成 zip は `zip` crate の writer、合成 PNG は `image` で生成。フォルダ冊・ZIP 冊・混在・壊れた zip（先頭だけ切り詰め）・画像 0 枚・深さ3の冊・日本語名・`2.png`/`10.png`・`__MACOSX`） | 単体 + 結合テスト: 発見される冊の集合が期待どおり（深さ3は拾わない、空フォルダは出ない）、頁順が自然順、壊れた冊は `broken` で `open` が Err、1000 エントリ zip が開ける |
| **p0-1b 索引 DB + CLI** | `index` モジュール（§2.2 のスキーマ、`user_version` 不一致で作り直し、冊の鍵による突き合わせ = 追加・更新・削除、50 冊ごとのトランザクション、構造索引のみ並列 = rayon で各 ZIP の中央ディレクトリだけ読む）。CLI `index` / `list`、`MANGA_VIEWER_DATA` 対応 | テスト: 初回→件数一致、2 回目は再スキャン 0 件、zip の追加/削除/更新が反映、broken が `status` に残る、`user_version` 破壊で作り直し。**ベンチ B-3(a,b)**: 合成 724 冊（各 28 頁、頁は小さくてよい）。`BENCH index_first100_ms`, `BENCH index_all_ms` |

## 7. 未確認・リスク

1. **`rusqlite` bundled が `cl.exe` 無しで通るか**（`cc` は PATH だけでなくレジストリ/vswhere でも探すので通る可能性が高いが未確認）。p0-0 が最初の関門。落ちたら Build Tools 導入（利用者判断）。代替で SQLite を諦めるのは利用者決定に反するので設計側では取らない。
2. **eframe の glow が実機の OpenGL で動くか**（極端に古いドライバ / RDP 環境）。p0-0 は build まで、実起動は p0-3a。
3. **B-1 部品予算 80 ms が実機で守れるか**。合成 PNG は実データより圧縮性が違う可能性（実データは線画で圧縮が効きやすく、デコードは速い側と見ているが未実測）。外れたら縮小を `fast_image_resize` へ替える → それでも外れたら「低解像度プレビュー → 原寸」の二段表示を p1 に回す。
4. **D: が HDD の場合の cold 読み**（表紙生成で 724 冊 × 先頭 1.4 MB ≈ 1 GB を読む）。B-3(c) と B-4 の cold 値は利用者実測でしか出ない。
5. **ZIP のファイル名エンコード**: UTF-8 フラグ無しの ZIP（CP932）は `zip` crate の既定解釈で文字化けしうる。頁順は連番名なので影響は小さいが、頁名を画面に出すなら要確認（p0 は頁名を出さない）。
6. **日本語フォントの TTC 読み込み**（egui の `FontData` の index 指定）が使っている egui の版で通るか。通らなければ `.ttf` 系（`msgothic` 以外）を探す順を足す。
7. **227 GB 級の実コレクションでの走査**: 724 冊の構造は 1 冊しか確認されていない。想定外の構造は broken または非表示になるだけで落ちない作りにする（A-6）。
8. フォルダ冊の鍵（フォルダ mtime + 画像サイズ合計）は、同サイズの画像差し替えを検出できない。許容（再索引は DB 削除で可能）。
