### カードの前提と違った点（重要）

- **JPEG→PNG 変換は存在しない。** `image` クレートは `[dev-dependencies]` のみ（テストの合成画像用）。本体は画像をデコードしておらず、ブラウザが復号している（`docs/p0-3-implementation.md` にも同記述）。
- **JS は 0 行。** `src/` に `<script>`・`addEventListener`・`keydown`・`fetch`・cookie・session・localStorage はいずれも無い（Grep で 0 件）。
- ブラウザ依存点は次の 3 つだけ。
  1. 画像の復号・拡大縮小（`<img style="max-width:100%">`）
  2. 頁送りは素の `<a href="/book/ID?p=N">prev/next</a>`。**キーボード操作は未実装**（矢印キーで頁送りはできない）
  3. 状態（現在頁）は URL の `?p=N` だけ。サーバ側にセッションなし
- **設計との食い違い。** `docs/p0-design.md` は「ブラウザ UI は却下」「egui/eframe を採用」と決めていた（§3.1、Tauri/WebView 系も却下）。実装は `serve` になっており、`docs/p0-status.md` も同じ食い違いを未決事項 5 として挙げている。ユーザーの「単独で起動する画像ビューアになぜブラウザが」という疑問は、**当初の決定どおりで正しい**。

### 補足

- C の「再利用できる」根拠は実測で示せる。`scan` / `book` / `index` / `natural` / `imgcheck` は `server` や HTTP を一切 `use` していない。`book.rs` の `read_page_bytes` が頁のバイトを返し、`index.rs` の `books()` / `books_under()` が一覧を返す。この 2 つで GUI が必要とする入口は揃っている。
- C で**まだ無い**もの（設計が想定していたのに未実装）: `decode`（バイト→画素、縮小）、`reader`（先読み・キャッシュ）、表紙サムネイル、日本語フォント登録、`eframe` 依存。つまり C は「server を GUI に差し替える」では済まず、設計 p0-2a〜p0-3c の残りを実装することになる。
- `imgcheck` は C でも有用（デコード前に壊れた頁を弾ける）。ただし `image` のデコード失敗でも壊れた頁は分かるので、役割は「軽い事前チェック」に縮む。
- D の再利用率が高いのは `server.rs` を温存するから。ただし、ユーザーの疑問の本質（ブラウザ的な作りを避けたい）には答えない。
- セッション数は P0 のこれまでの 1 カード 1 セッション規模からの**推定**。実測ではない。eframe の glow が実機の OpenGL で動くかは未確認（`p0-design.md` リスク 2）。

## 3. 推奨

**C（egui ネイティブ窓）を目標にする。** ただしいきなり一覧まで作らず、まず「1 冊を開いて矢印キーで読める窓」を最短で出す。

理由:

1. ユーザーの意図（単独で起動する画像ビューア）と、既に合意済みの設計（`p0-design.md` §3.1）の両方に合う。A・B・D は「ブラウザ UI は却下」と矛盾したままになる。
2. B は安いが、見た目と中身がブラウザのままで、キー操作・先読みという「高速ビューア」の中核が手に入らない。ブラウザが復号するため頁送りの速度も制御できない。
3. C に必要な土台（scan / book / index / natural / imgcheck、テスト 44 本）は既にある。足りないのは decode・reader・GUI だけで、書く範囲が明確。
4. C の最大リスクは eframe が実機で起動するかと日本語フォント。最初のカードでこれを潰せば、失敗しても B に退避できる（B は 1 カードで足せる）。

B をつなぎとして先に入れる必要は薄い。**ただし C が詰まった場合の保険**として、p0-6 の最初に「eframe が起動するか」だけを確かめる。

## 4. 次のカード案（そのまま貼れる粒度）

### MV-p0-6b: eframe の関門 + 1 頁表示（最小）
- `cargo add eframe`（`default-features=false`, `["glow","default_fonts"]`）、`image`（`["png","jpeg","webp","gif"]`）を本体依存に。`cargo build --release` が通ること。落ちたら default features に戻し、報告に書く。

## 5. ユーザーに出す一行の回答

> 今の `serve` は、画像の復号と表示をブラウザに任せているだけの仮の作りで、もともとの設計（egui の単独ウィンドウ）とは別物です。単独で起動するビューアにするなら、索引・zip・画像検証はそのまま使えるので、足りない復号と表示窓を作る方向（案 C）を勧めます。

## 6. MV-p0-7c 判断: `serve` の存廃と serve/view の挙動差

### 6.1 存廃の判断: **残す。ただし「デバッグ専用」と明文化し、P0 完了条件から外す**

- P0 の最終形は native `view`（§3）。ユーザー向けの閲覧手段として `serve` を案内しない。
- 残す理由: ブラウザで索引・頁・壊れ判定を目視確認できる開発用の窓口として安い（`server.rs` は std のみ、外部依存なし、追加保守はほぼ無い）。`tests/server.rs`・`tests/image_check.rs` の試験も `imgcheck` と索引の回帰網として効いている。
- 保守コストの懸念は「挙動差の同期」だった。これは**検証の入口を `decode::decode_rgba` に一本化**することで、差を増やさない形にした（下記）。以後 view 側の検証が変わっても serve は同じ関数を呼ぶので自動で追随する。
- 実削除は**しない**。削除するなら人間の承認を待つ（削る場合は `server.rs`・`tests/server.rs` 8 本と `image_check.rs` の serve 依存分）。`src/server.rs` の冒頭にも「デバッグ専用」と書いた。

### 6.2 4 差への決定

| # | 差 | 決定 | 内容 |
|---|---|---|---|
| 1 | 壊れた本体画像（署名・終端は正常で中身だけ壊れ）: serve は 200、view はエラー | **収束** | serve の `/page`・`/image` も `decode_rgba` で実復号し、失敗なら **422**。デバッグ中に「serve では出るのに view では出ない」と誤解させるのが最も害が大きいため。代償: 配信のたびに実復号するのでデバッグ用途では遅い（許容） |
| 2 | 範囲外頁: serve は 404、view は最終頁に丸め | **意図的残置** | serve は URL で頁を指すので存在しない頁は 404 が HTTP として正しい。view の `--page` は人間が打つ CLI 引数で、丸めた方が親切。入口の性質が違う（cli.rs のドキュメントにも記載済み） |
| 3 | 形式判定: serve は拡張子、view は magic | **意図的残置（実害なし）** | 実際は両者とも Content-Type/形式は magic で決める。serve の拡張子判定は「未対応形式の頁か」の入口ゲートだけで、`Book` が頁として拾う拡張子（png/jpg/jpeg/webp/gif）は `content_type()` の対応と一致するため、このゲートは現状で発火しない。拡張子が嘘の場合（.jpg 名で中身 PNG）は既存テストどおり両者とも magic に従う |
| 4 | 壊れ画像の文言 | **収束** | serve も `この頁は表示できません: {DecodeError}` に統一（view と同じ文字列。`DecodeError` の文言は両者共通の 1 箇所）。署名不正も本体破損も 422 に統一（従来は署名不正のみ 404 で「壊れた画像です」） |

### 6.3 人間判断が要る点（確定していない）

- serve を将来**削除**するか（上記のとおり提案は「残す」止まり）。
  - **2026-10-31 決定（利用者、#7）: 削除する。** ブラウザ経由の閲覧は要らない。`serve` サブコマンド・`src/server.rs`・`tests/server.rs` を消し、serve 経由で見ていた頁ごとの判定と修復の種類の試験は `load_page` / `decode_rgba` を直接見る形に移した。下の 422/404 の使い分けも serve と一緒に消えたので決定不要。
- 422 と 404 の使い分け: 範囲外・未登録の冊は 404、壊れ頁は 422、冊自体が壊れ（`Status::Broken`）は従来どおり 404 のまま。冊レベルの壊れも 422 にそろえるかは未決（view 側は冊が壊れていれば起動時エラーで落とすので、挙動は近い）。

### 6.4 変更したテスト

- `tests/image_check.rs`: 壊れ頁の期待を 404→422、文言を「この頁は表示できません」に更新。署名だけのダミー JPEG/WebP/GIF は実復号できないため、配信される側のフィクスチャは `tests/common` に足した本物の符号化データ（`real_jpeg_bytes` 等）に差し替えた。`jpeg_bytes` 等のダミーは `imgcheck` 単体の試験用に残す。
- 追加: `body_corrupt_image_is_422_with_view_wording`（imgcheck は通るが復号できない PNG を `/page`・`/image` で 422・view と同じ文言にする）。
- テスト本数: 70 → **71**（実測: `cargo test` 全バイナリ合計 14+10+12+16+7+8+4）。
