# P0 ゴール判定（監査者 Claude）

対象: branch `qwen-p0`、HEAD は e3d5360（本文書の commit を除く）。2026-10-31。
漫画実データ（`D:\books`・`D:\torrent`）には一切触れていない。判定はすべて合成データでの再測と過去の監査報告に基づく。

## 結論: **P0 完了**（「実際に動くもの」のライン = scan → index → serve → imgcheck）

ただし**この「ライン」は `docs/p0-design.md` の P0 とは別物**である。下の「設計との乖離」を必ず読むこと。
乖離は残作業ではなく、利用者が次段階の範囲として決める事項として扱う。

## 1. 各段の監査判定

| 段 | 判定 | 根拠 |
|---|---|---|
| p0-1a 走査・冊・頁リスト | 合格（所見 3 件） | p0-1a 監査報告 |
| p0-2a/2b 索引の永続化 | 直してから → p0-2fix へ | p0-2a/2b 監査報告（変異 7/7 生存） |

| p0-3 serve（一覧・頁・画像） | **合格** | p0-3 監査（serve 実走で 11 頁のバイト数一致・41 本） |
| p0-4 imgcheck | 条件つき → **合格** | 本 fix（e3d5360）の再監査。変異 5/5 再撃墜、52 本、4 門 exit 0 |

p0-4 の条件（生存変異 5 本の固定）は **解除可**。条件は「テストが境界・アンカーを固定していない」ことだけで、実装自体の誤りではなかった。

## 2. 残存する既知の制限と切り分け

| 制限 | 区分 | 理由 |
|---|---|---|
| 圧縮データ内部が未検証（ヘッダと終端が正しく中身だけ壊れた画像は通る） | **次段階** | 検出にはデコードが要る。設計の p0-2a（decode）の領分。imgcheck は途中切れを捕まえる設計で、その範囲は固定済み |
| PNG の CRC 未検証 | **P0 内で許容** | 実装メモ・コード冒頭に明記。途中切れの検出には影響しない。CRC を見るなら decode 段で一括して扱う方が自然 |
| slowloris（遅い接続）耐性なし | **P0 内で許容** | 127.0.0.1 待受のみ（p0-3 監査所見 3）。外部公開するなら次段階で再検討 |
| 実在漫画で未検証 | **次段階（p0-5）** | 利用者と共に行う取り決め。合成データでの動作は確認済みだが、実データの構造・サイズ・名前は未知 |
| `foreign_keys=OFF` への変異が生存（p0-2fix の N7） | **次段階（p0-2c で表紙を書く時）** | 誤解を避けるため補足: コードは接続ごとに `PRAGMA foreign_keys=ON`（`src/index.rs:437`）で、OFF なのは現状ではない。`covers` に書く処理がまだ無く、CASCADE は観測不能なので変異が生き残るだけ。表紙を書き始める段で「冊を消すと covers も消える」テストを同時に足すこと |
| 等価変異 M06・M08 の生存 | **対応不要** | 観測できる差が無い（冗長ガード） |

P0 のライン内で未解決の欠陥・条件つき判定は残っていない。

## 3. 設計との乖離（利用者の判断が要る）

`docs/p0-design.md` が想定した P0 は、ネイティブ GUI（egui）・画像デコードと縮小・頁キャッシュ/先読み・表紙サムネイル・
速度の合格線 B-1〜B-5（頁送り p95 ≤ 100 ms、起動→一覧 ≤ 1.0 s など）の実測を含む。
qwen-p0 の実装はこれと異なる形になっている:

- UI は GUI ではなくローカル HTTP サーバ（`serve`、127.0.0.1）。設計は「ブラウザ UI は却下」としていた。
- 依存に egui・image（本体側）・memory-stats が無く、decode・reader・covers 書き込み・GUI・autopilot は未実装。
- 速度の合格線（B-1〜B-5）は一度も測っていない。

本判定の「P0 完了」は、カードが定義した **動くもの（scan → index → serve → imgcheck）が欠陥なく動く** という意味に限る。
設計書の P0 としては未達の項目が多い。これを「P0 の残作業」とするか「方式変更で次段階の範囲」とするかは設計判断であり、
監査者が勝手に決めない。次段階の候補（優先順の提案ではなく列挙）:

1. 実在漫画での検証（p0-5。利用者と共に）
2. 速度の合格線の実測（合成 724 冊での起動→一覧、頁送り）
3. decode（圧縮内部・PNG CRC の検出もここ）
4. 表紙サムネイル（`covers` 書き込み + CASCADE のテスト）
5. 閲覧 UI の方式（設計の egui か、現状のブラウザ配信か）の決定

## p0-8a 破損本体の自動修復
- `decode_rgba`: strict → 終端マーカー（JPEG EOI / PNG IEND）で切って strict → imgcheck の終端検査を外した lax 復号、の順。成功時 `Decoded.repair` に `TrailingGarbage{len}` / `Truncated`。先頭側破損・署名不明・巨大寸法は従来どおりエラー。
- 仕様の順序から変更: 「切り詰め」を lax より先に試す（正確に直せるうえ、印が `trailing-garbage` と正しく付くため）。
- view: 修復頁は黄色の「修復して表示: …」を画像の上に出す（頁送りで消える）。serve: `X-MV-Repaired: trailing-garbage|truncated`。末尾ゴミは切って返し、truncated は元バイトのまま返す。
- 副作用: EOI だけ欠けた JPEG・IEND/トレーラだけ欠けた PNG/GIF は、全画素が読めるため 422 → 200+印 に変わった（image_check の期待値を更新）。
